# Домашняя работа: классификация водителей

Основной файл с кодом и результатами — [task_classification.ipynb](task_classification.ipynb). Исходный архив с данными — [`archive/task_classification.zip`](../archive/task_classification.zip). Задача: по признакам водителя предсказать, воспользуется ли он страховкой в следующем году. Ответ бывает 0 или 1, поэтому это **бинарная классификация**.

## Что я сделал

1. Сначала разделил исходных водителей на обучение и тест, затем независимо сбалансировал обе части до 100 000 строк в каждой. Тест нужен для итоговой оценки на данных, которые модель не видела при обучении. Числовые признаки масштабировал: среднее около нуля, разброс около единицы.
2. Обучил логистическую регрессию. Она вычисляет вероятность класса 1; при пороге 0,5 получает ответ 0 или 1. На отдельной валидационной части с разделением по исходным водителям сравнил несколько значений `C` и выбрал `0.01`. Чем меньше `C`, тем сильнее L2-регуляризация: она сдерживает большие коэффициенты модели. На тесте получил accuracy **0.5876** и ROC-AUC **0.6201**.
3. Посмотрел, как меняется log loss по итерациям без регуляризации и с L2-регуляризацией (`C=0.001`). Log loss штрафует уверенные неправильные предсказания. На каждом из двух графиков есть линии обучения и теста; оси одинаковые. Регуляризация ограничивает сложность модели, но слишком сильная может ухудшить подгонку.
4. Заменил категориальные признаки на **one-hot**: для каждого значения категории создаётся отдельный признак 0/1. Это убирает искусственный порядок между категориями. Число признаков выросло с **57 до 227**. Тестовый ROC-AUC вырос до **0.6265**, accuracy до **0.5897**. Обучение заняло около **2.52 с**.
5. Попробовал **счётчики**: категорию заменил долей положительных ответов среди обучающих объектов той же категории. Если категория не встречалась, использовал общую долю положительного класса. Получил тестовый ROC-AUC **0.6227** и обучение около **0.11 с**. Это быстрее one-hot, но здесь качество немного ниже.
6. У наивных счётчиков есть **утечка целевой переменной**: при вычислении признака обучающего объекта используется его собственный ответ. Поэтому сравнил два способа, где ответ текущего объекта не используется: подсчёт по предыдущим объектам и по пяти фолдам. Тестовый ROC-AUC составил **0.6237** и **0.6242** соответственно. В этом запуске способ по фолдам немного лучше.

## Как понимать оценки

- **Accuracy** — доля верных ответов при пороге 0,5. Например, 0.5897 означает около 59,0% верных ответов.
- **ROC-AUC** показывает, насколько хорошо модель ставит положительные объекты выше отрицательных по предсказанной вероятности. 0.5 соответствует случайному ранжированию, 1.0 — идеальному. Здесь главное сравнение моделей ведётся по ROC-AUC.
- Время обучения зависит от компьютера и конкретного запуска; важнее порядок величин и сравнение способов кодирования.

## Возможные вопросы преподавателя

**Зачем балансировать классы?** В исходных данных положительный класс редок. При равных долях классов проще сравнить методы и интерпретировать accuracy. Результаты относятся именно к такой сбалансированной выборке.

**Почему масштабирование обучают на train?** Среднее и разброс вычисляют по обучающим данным, а к тесту применяют уже найденные параметры. Так тест не влияет на подготовку модели. При строгом подборе `C` масштабирование следует отдельно обучать внутри каждого обучающего разбиения валидации.

**Почему обычные числа плохо подходят категориям?** Числа 1, 2 и 3 создают видимость порядка и расстояния, хотя категории могут быть просто разными названиями.

**Что означает `C`?** Это параметр, обратный силе регуляризации. Маленькое `C` сильнее сдерживает коэффициенты.

**Чем опасна утечка в счётчиках?** Модель частично узнаёт правильный ответ через входной признак. Оценка на обучении становится слишком оптимистичной, а на новых данных такой подсказки нет.

**Как работают фолды?** Обучающую выборку делят на пять частей. Для каждой части средние по категориям считают на остальных четырёх. Для теста средние считают по всей обучающей выборке, не используя метки теста.

## Подробный разбор от начала до конца

### 1. Что лежит в данных

Каждая строка — водитель. Столбцы содержат 57 признаков, а `target` — правильный ответ: 1, если водитель воспользовался страховкой, и 0 в противном случае. `target` отделяется от признаков: модель должна предсказывать его, а не получать как вход. `index_col=0` убирает идентификатор из признаков.

В ячейке 7 исходные строки сначала разделяются с сохранением долей классов. Затем из каждой части выбираются по 50 000 строк каждого класса. `replace=True` разрешает повторения внутри части; `random_state` и генератор с seed 910 делают выбор воспроизводимым.

**Исправленное разделение:** исходных водителей сначала разделяют на train и test, а затем независимо балансируют каждую часть. По 50 000 строк каждого класса дают по 100 000 строк в каждой части. Повторные копии одного водителя не пересекают границу train/test. Внутренняя валидация и фолды также учитывают группы исходных водителей.

### 2. Масштабирование

`StandardScaler` для каждого признака вычисляет среднее и стандартное отклонение на обучении, затем преобразует значение примерно по формуле `(значение − среднее) / отклонение`. Тест преобразуется теми же параметрами. Это помогает обучению модели, когда столбцы имеют разный численный масштаб. В первой части задания категориальные коды пока тоже обрабатываются как числа.

### 3. Что делает логистическая регрессия

Модель складывает признаки с весами: `z = b + w₁x₁ + ... + wₙxₙ`. Функция `1 / (1 + exp(−z))` превращает результат в вероятность класса 1. При пороге 0.5 вероятность превращается в ответ 0 или 1. Несмотря на название, это метод классификации.

Регуляризация добавляет штраф за слишком большие веса. В L2 штрафе участвуют квадраты весов. `C` обратно связан с силой регуляризации: меньше `C` — сильнее штраф. В ноутбуке проверены `0.01`, `0.1`, `1`, `10`; по валидационному ROC-AUC выбрано `0.01`. Различия оценок очень небольшие, поэтому нельзя говорить, что это доказанный глобальный оптимум. После выбора модель обучена на всём train и оценена на test.

**Подбор без утечки:** GroupShuffleSplit отделяет валидацию по исходным водителям, а Pipeline обучает StandardScaler только на внутренней обучающей части. Валидация преобразуется готовым scaler.

### 4. Как читать три метрики

**Accuracy** — доля верных ответов при выбранном пороге 0.5. Базовое значение `0.5876` означает около 58.76% правильных ответов на сформированном тесте. Поскольку классы сбалансированы, простое предсказание одного класса дало бы около 50%.

**ROC-AUC** показывает качество ранжирования по вероятности. Представьте случайную пару из положительного и отрицательного объектов: значение `0.6201` означает, что примерно в 62.01% таких пар модель даст положительному объекту более высокий балл. Случайное ранжирование даёт около 0.5, идеальное — 1. Эта метрика не привязана к одному порогу.

**Log loss** учитывает сами вероятности. Уверенный неверный ответ получает большой штраф. Меньше — лучше. Постоянная вероятность 0.5 на сбалансированных данных даёт около 0.693.

### 5. Графики регуляризации

В ячейке 14 сравниваются модель без штрафа и модель с L2 при `C=0.001`. `max_iter=1` останавливает каждый вызов обучения после одной итерации, а `warm_start=True` позволяет следующему вызову продолжить с предыдущих весов. Поэтому после каждого шага можно измерить loss на train и test. Точка 0 — прогноз 0.5 до обучения. Показаны 20 шагов, а оси двух графиков совпадают.

Если train loss падает, модель лучше подгоняется к обучающим данным. Если test loss при этом растёт, это признак переобучения. Слишком сильная регуляризация способна привести к недообучению. На графиках показан обычный `log_loss`, **без L2 штрафа**, хотя при обучении второй модели штраф участвует. Не стоит утверждать, что графики обязательно доказывают сильное переобучение: нужно смотреть на форму конкретных кривых.

### 6. Почему категории нельзя просто считать числами

Код категории 3 не обязательно означает «больше» категории 2. Для модели числа задают порядок и расстояние, которого в реальности может не быть. Категориальные столбцы определяются по окончанию имени `_cat`.

**One-hot:** у каждого значения категории появляется отдельный индикатор 0 или 1. Например, три цвета превращаются в три столбца. `handle_unknown="ignore"` позволяет обработать новую категорию в тесте. `ColumnTransformer` одновременно масштабирует остальные признаки. Число столбцов выросло с 57 до 227; тестовый ROC-AUC стал `0.6265`, accuracy `0.5897`. Обучение заняло `2.52 с`. Это лучше базового ROC-AUC примерно на `0.0064`.

**Счётчики:** категория заменяется долей положительных меток среди обучающих объектов этой категории. Если у 3 из 10 объектов категории A `target=1`, её код равен 0.3. Для неизвестной категории используется общая доля положительного класса, здесь 0.5. Тестовый ROC-AUC стал `0.6227`, accuracy `0.5872`, время обучения `0.11 с`.

Время здесь измеряет только `model.fit`, а не подготовку признаков. Кроме того, для one-hot используется `saga`, для других моделей `lbfgs`. Поэтому нельзя объяснять всю разницу времени только кодированием: влияет и алгоритм оптимизации.

### 7. Утечка в наивных счётчиках

Если для обучающей строки среднее по категории вычислить вместе с её собственной меткой, признак частично раскрывает правильный ответ. В крайнем случае категория встречается один раз: тогда её счётчик в точности равен `target` этой строки. Для теста его метка не используется, поэтому возникает несоответствие между подготовкой train и test. Даже небольшой разрыв метрик train/test не отменяет эту проблему: она следует из формулы расчёта.

В ячейке 23 реализованы два способа избежать собственной метки:

1. **По предыдущим строкам.** Перед вычислением признака текущей строки учитываются только уже просмотренные строки. После вычисления её метка добавляется к сумме. Для первого появления категории используется 0.5. Порядок строк имеет значение; в ноутбуке это порядок после случайного разделения, а не временной порядок.
2. **По пяти фолдам.** Train делится на пять частей с помощью StratifiedGroupKFold: копии одного водителя остаются в одной части. Для каждой части средние категорий считают на остальных четырёх. Получается признак для всех обучающих строк, рассчитанный без их собственных меток. Для test средние берутся по всему train: метки test при этом не используются.

| Способ | ROC-AUC train | ROC-AUC test | Accuracy test | Время `fit` |
|---|---:|---:|---:|---:|
| По предыдущим строкам | 0.6352 | 0.6237 | 0.5890 | 0.10 с |
| По пяти фолдам | 0.6348 | 0.6242 | 0.5901 | 0.12 с |

Разница тестового ROC-AUC равна 0.0005 — она мала. По одному запуску нельзя уверенно сказать, что фолды всегда лучше.

### 8. Все результаты рядом

| Представление категорий | ROC-AUC test | Accuracy test | Время `fit` |
|---|---:|---:|---:|
| Исходные числовые коды | 0.6201 | 0.5876 | 0.11 с |
| One-hot | 0.6265 | 0.5897 | 2.52 с |
| Наивные счётчики | 0.6227 | 0.5872 | 0.11 с |

## Вопросы, которые могут задать дополнительно

**Зачем train, validation и test?** На train подбираются веса, на validation выбирают настройки вроде `C`, test используют для итоговой оценки после выбора.

**Почему ROC-AUC и accuracy различаются?** Accuracy использует один порог 0.5; ROC-AUC оценивает порядок вероятностей по всем порогам.

**Почему нельзя считать среднее категории по всему датасету?** Тогда метки тестовых строк попадут в признаки, и оценка станет недостоверной.

**Почему для теста можно использовать средние по всему train?** Метки train известны, а метки test в расчёте не участвуют.

**Почему 0.5 для неизвестной категории?** Это доля положительного класса в созданной сбалансированной выборке, нейтральная оценка при отсутствии сведений о категории.

**Реализован ли метод опорных векторов?** Нет. Он упомянут в заголовке исходного шаблона, но задания и код ноутбука посвящены логистической регрессии и кодированию категорий.
